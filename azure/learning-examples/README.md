# Azure Terraform learning examples

These are new, independent configurations. They do not reuse, migrate, or modify
the resources or state in the parent `azure` directory. `prod` is a second learning
environment, not a production-ready deployment.

## Folder and state boundaries

```text
learning-examples/
  dev/
    provider.tf                 # Requirements, authentication, local backend
    main.tf                     # Calls the shared module with dev inputs
    variables.tf                # Input declarations and safe defaults
    outputs.tf                  # Re-exports the module's outputs
    terraform.tfvars.example    # Copy to terraform.tfvars for local values
    terraform.tfstate           # Generated after apply; do not commit
  prod/
    provider.tf
    main.tf
    variables.tf
    outputs.tf
    terraform.tfvars.example
    terraform.tfstate           # A different generated state; do not commit
  modules/
    lab/
      versions.tf               # Provider source and CLI requirements
      variables.tf              # Typed inputs, validation, locals, tags
      main.tf                   # Resource group, VNet, subnets, optional NIC
      outputs.tf                # for expression and splat examples
```

**State files are generated by Terraform, not hand-written sample JSON.**
The local backend path is relative to each root's working directory:
`dev/terraform.tfstate` and `prod/terraform.tfstate` are separate files.
Each root also gets its own provider lock file during initialization.
The shared child module has no separate state; its resources live in the calling
root's state with addresses such as `module.lab.azurerm_subnet.lab["app"]`.

Terraform reads all `.tf` files in the working directory together, but does not
automatically read child folders. Run commands from `dev` or `prod`, **not** from
the parent `azure` directory, `learning-examples`, or the shared module directory.
The existing parent configuration is not required for these examples.

## Concepts demonstrated

| Concept | Where to look |
|---|---|
| Provider requirements versus CLI version | Each root's `provider.tf` |
| Provider inheritance/passing | The `providers` map in each root's `main.tf` |
| Separate state and lifecycles | The independent dev/prod local backends |
| Typed variables and custom validation | Module `variables.tf` |
| Values files and defaults | Each root's `terraform.tfvars.example` |
| Locals, interpolation, and `merge` | Module `variables.tf` |
| Implicit dependencies | VNet references the resource group; subnets reference the VNet |
| Stable `for_each` instances | Subnets keyed by `app` and `data` |
| Conditional `count` | NIC has zero or one instance |
| A `for` expression | Subnet IDs exported as a keyed object |
| Splat expressions | NIC IDs and private IPs, empty when disabled |
| Address migration | A `moved` block preserves the previous NIC address binding |
| Module/root outputs | Child exports and root re-exports |

Both environments create a resource group, a VNet, and two subnets.
Enabling the NIC adds an unattached private network interface in the app subnet.
No VM, OS disk, public IP, or SSH key is configured.
The default CIDRs are valid, non-overlapping examples; if you edit them, ensure
subnets remain inside the VNet range and do not overlap.

## Authentication

In the same PowerShell terminal used to run Terraform:

```powershell
$env:ARM_CLIENT_ID       = "<service-principal-client-id>"
$env:ARM_TENANT_ID       = "<tenant-id>"
$env:ARM_SUBSCRIPTION_ID = "<subscription-id>"
$secret = Read-Host "Replacement service principal secret" -AsSecureString
$env:ARM_CLIENT_SECRET = [System.Net.NetworkCredential]::new("", $secret).Password
Remove-Variable secret
```

Use a fresh, unexposed secret. The Azure provider reads these variables directly:
`TF_VAR_azure_client_secret` from the parent example is not used here.
Alternatively, use `az login` with the correct subscription and remove conflicting
service-principal environment settings. Do not put credentials in `.tf` or values
files. The identity needs permissions for the resources you plan to create.

The AzureRM version constraint matches the existing examples (`~> 3.0.2`).
The minimum CLI remains 1.2; `required_version` is not a provider
version. Azure permissions, provider registration, regional availability, and
subscription quotas must also permit deployment.

## Try dev first

From the repository root:

```powershell
Set-Location ".\azure\learning-examples\dev"
Copy-Item -LiteralPath ".\terraform.tfvars.example" -Destination ".\terraform.tfvars"
terraform init
terraform fmt -check
terraform validate
terraform plan -out="lab.tfplan"
terraform show "lab.tfplan"
```

Initialization downloads providers and configures the backend; validation and
planning do not create the proposed cloud resources. Review the account, names,
region, and proposed actions before deliberately deploying:

```powershell
terraform apply "lab.tfplan"
terraform output
terraform state list
```

Applying a saved plan does not ask for confirmation again. Never commit state,
saved plans, secret-bearing values files, or private keys. Existing repository
ignore rules exclude state, plans, and `.tfvars`; `.tfvars.example` is a safe
tracked template. Commit the root `.terraform.lock.hcl` files.

## Opt in to the network interface

Set `enable_nic = true` in your local `terraform.tfvars`, then generate and
review a new plan. The default is false to demonstrate a zero-instance `count`.
The NIC uses a dynamically allocated private IP and is not attached to a VM.
It provides no SSH endpoint or public connectivity. Enabling/disabling it changes
the NIC instance, not the subnets.

If you used the earlier VM example, replace `enable_vm` with `enable_nic` in
your local values file and remove `ssh_public_key`. To retain an already deployed
NIC, set `enable_nic = true`. The module's `moved` block maps its old `vm` label to
`lab` without replacement caused solely by that rename.
The next normal plan will propose deleting any VM previously managed by this
module because its resource block has been removed. Review those deletions and
any disk implications before applying. Discard old saved plans: they still
contain the previous VM configuration. No state or cloud resources are changed
just by editing these files.

## Compare prod's separate state

From dev:

```powershell
Set-Location "..\prod"
Copy-Item -LiteralPath ".\terraform.tfvars.example" -Destination ".\terraform.tfvars"
terraform init
terraform plan
```

Observe the `tf-learning-prod` names and `10.20.0.0/16` network.
Prod does not read or adopt dev's resources. Applying prod is a separate deployment;
destroying dev does not destroy prod. Do not copy a state file between the folders.
The `prod` label does not change accounts or security permissions automatically.

For remote state later, choose a supported backend with distinct keys for each
root, such as `learning/dev.tfstate` and `learning/prod.tfstate`, and migrate each
root independently with `terraform init -migrate-state`.

## Safe exercises

1. Inspect resource addresses with `terraform state list` after applying.
2. Change a tag and plan an in-place update.
3. Add a third subnet with a unique map key and non-overlapping CIDR. Only the
   added key should need creation; existing keyed instances should retain identity.
4. Toggle the optional NIC and inspect the proposed creates/deletes.
5. Rename a Terraform resource label using a reviewed `moved` block, not by
   changing the Azure object's name. Cloud-name changes can require replacement.

The dev/prod root files have no provisioners and do not call the parent `ansible.tf`.
Use a new plan for every exercise. Do not run state-editing experiments on the
original parent state or on real production infrastructure.

## Cleanup

Run separately inside each environment that you applied:

```powershell
terraform plan -destroy -out="cleanup.tfplan"
terraform show "cleanup.tfplan"
terraform apply "cleanup.tfplan"
if (Test-Path Env:\ARM_CLIENT_SECRET) {
  Remove-Item Env:\ARM_CLIENT_SECRET
}
```

The apply executes the deletions immediately. Never place unrelated resources
inside these lab resource groups: deleting a group can delete its contents,
including resources not managed in this state. Provider protection against
non-empty group deletion is enabled, but is not a substitute for reviewing plans.
Deleting sample files or state does not delete cloud resources. Keep state until
cleanup succeeds; deleting lab resources does not eliminate costs of resources elsewhere.

## Offline mocked tests

With Terraform 1.7+ and the provider installed, run from dev:

```powershell
terraform init
terraform test
```

The tests use a mocked Azure provider and plan-only runs. They check stable subnet
keys, the default absence of a NIC, the NIC opt-in, and invalid-environment
rejection. They do not contact Azure or deploy infrastructure.
Mocks verify Terraform wiring, not Azure permissions
or service-side validation.

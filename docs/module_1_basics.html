Topic 01 • Infrastructure Syntax Specification

HashiCorp Configuration Language (HCL2)

HCL2 is a declarative, human-readable language designed specifically for defining infrastructure graphs. It balances machine-parsable JSON structures with concise user ergonomics, structural type validation, and dynamic expression evaluation.

HCL Syntax Spec Type System Specs

Visual Structural Breakdown of an HCL Block

1. Block Type

Defines the fundamental construct (e.g., resource, provider, variable).

2. Block Labels

Specifies target provider type and the unique identifier instance name.

3. Arguments & Attributes

Key-value pairs assigning values or expressions to properties.

resource "aws_s3_bucket" "enterprise_audit_logs" { // Block Type + 2 Labels
bucket = "corp-audit-logs-2026-prod" // Attribute Key = Value (String)
force_destroy = false // Boolean primitive
tags = { // Map Primitive
Environment = "Production"
ManagedBy = "Terraform"
}
}

Property Reference: HCL Data Types & Constructs

Searchable guide for native language primitives and dynamic block arguments.

Construct / Element Type / Category Required Default Value Description & Scope
string Primitive Type N/A "" Sequence of Unicode characters wrapped in double quotes. Supports string interpolation `"${var.name}"`.
number Primitive Type N/A 0 Integer or floating-point value (e.g., `10`, `3.14`). Automatic conversions occur in HCL.
bool Primitive Type N/A false Boolean truth value (`true` or `false`).
list(<TYPE>) Complex Collection N/A [] Ordered sequence of values of a uniform type indexed starting at 0.
map(<TYPE>) Complex Collection N/A {} Collection of key-value pairs where keys are strings and values share a common type.

Topic 02 • Provider Plugins & Authentication

Providers, Source Registries & Authentication

Providers are executable plugins that translate HCL declarations into downstream cloud platform API calls. Terraform utilizes the `required_providers` block to enforce version locks, source namespaces, and regional authentication contexts.

Provider Requirements Docs Terraform Registry

Provider Plugin Initialization Architecture

1. HCL Declarations
required_providers { aws = "5.0" }
2. terraform init
Downloads binary to .terraform/providers
3. gRPC Client Call
Calls Cloud APIs via SDK credentials

Provider Block Configuration & Aliases

Configure default and multi-region provider instances.

providers.tf (AWS Multi-Region Configuration) 
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.30.0"
    }
  }
}

# Default Primary Region
provider "aws" {
  region = "us-east-1"
}

# Secondary Region Provider Alias
provider "aws" {
  alias  = "west"
  region = "us-west-2"
}
providers.tf (Azure Provider with Features) 
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.80.0"
    }
  }
}

provider "azurerm" {
  features {}
  subscription_id = "00000000-0000-0000-0000-000000000000"
}
providers.tf (GCP Provider Block) 
terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.10.0"
    }
  }
}

provider "google" {
  project = "corp-prod-infrastructure"
  region  = "us-central1"
}

Provider Requirements Attributes

Attribute Required Type Description
source Yes string Global hostname and namespace (e.g., `hashicorp/aws`). Defaults to `registry.terraform.io`.
version Optional string Semantic version constraint (e.g., `~> 5.0` allows patch/minor upgrades).
alias Optional string Secondary identifier for configuring multiple configurations of the same provider.

Topic 03 • Resource Lifecycle & Graph Management

Resource Blocks, Addressing & Implicit Dependencies

Resources represent infrastructure components. Terraform builds a Directed Acyclic Graph (DAG) to determine optimal execution order, automatically managing implicit dependencies established by attribute references between resources.

Resource Language Spec

Implicit Dependency Graph Linkage

Referencing outputs from resource A inside resource B creates automatic execution graph ordering.

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "web" {
  # IMPLICIT DEPENDENCY CREATED HERE VIA VPC_ID REFERENCE
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}
resource "azurerm_resource_group" "rg" {
  name     = "rg-core"
  location = "eastus"
}

resource "azurerm_virtual_network" "vnet" {
  name                = "vnet-prod"
  resource_group_name = azurerm_resource_group.rg.name
  location            = azurerm_resource_group.rg.location
  address_space       = ["10.0.0.0/16"]
}
resource "google_compute_network" "vpc" {
  name                    = "custom-vpc"
  auto_create_subnetworks = false
}

resource "google_compute_subnetwork" "subnet" {
  name          = "subnet-us"
  ip_cidr_range = "10.0.1.0/24"
  network       = google_compute_network.vpc.id
}

Resource Meta-Arguments Reference

Meta-Argument Type Description
depends_on list(resource) Explicitly specifies dependencies Terraform cannot automatically infer.
count number Creates multiple identical resource instances indexed by integer (`count.index`).
for_each map / set(string) Creates dynamic resource instances identified by custom string keys (`each.key`).

Topic 04 • Input Variables, Validation & Sensitive Outputs

Input Parameterization & Output Contracts

Input variables serve as configurable parameters for custom module reusability, complete with validation rules. Output values expose resource attributes to parent modules or external orchestration CLI commands.

Input Variables Doc

Input Validation & Sensitive Flags

Validate environment strings and mask confidential passwords in console logs.

variable "environment" {
  type        = string
  description = "Target Deployment Tier"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be dev, staging, or prod."
  }
}

variable "db_password" {
  type      = string
  sensitive = true
}

output "rds_endpoint" {
  value = aws_db_instance.main.endpoint
}
variable "admin_password" {
  type        = string
  sensitive   = true
  description = "Administrator password for Azure VM scale set."
}

output "vm_public_ip" {
  value     = azurerm_public_ip.pip.ip_address
  sensitive = false
}
variable "gcp_region" {
  type    = string
  default = "us-central1"
}

output "gke_cluster_name" {
  value = google_container_cluster.primary.name
}

Variable Precedence Order (Lowest to Highest)

Precedence Level Source Mechanism Example Syntax
1 (Lowest) Default block value default = "us-east-1"
2 Environment Variables export TF_VAR_region="us-west-2"
3 terraform.tfvars file region = "eu-central-1"
4 (Highest) Command Line Flag terraform apply -var="region=ap-south-1"

Topic 05 • Command Lifecycle Workflow & Execution Engine

Terraform Core Lifecycle Commands

The core operational flow follows a strict 4-stage lifecycle: `init` (plugin download), `plan` (execution graph delta generation), `apply` (cloud state mutation), and `destroy` (deprovisioning).

CLI Commands Manual

Standard Operational Sequence

1. terraform init Initialize working directory
2. terraform plan Preview proposed state diff
3. terraform apply Execute infrastructure mutations
4. terraform destroy Teardown managed resources

CLI Command Reference & Flags

Command Primary Purpose Common Operational Flags
terraform init Downloads provider plugins and sets up backend state modules. -upgrade, -backend-config=path
terraform plan Compares real-world state against code to generate execution diff. -out=tfplan, -var-file=prod.tfvars
terraform apply Executes planned actions against Cloud Provider APIs. -auto-approve, tfplan
terraform fmt Rewrites configuration files to canonical format and style. -check, -recursive
terraform validate Verifies whether configuration files are syntactically valid. -json
